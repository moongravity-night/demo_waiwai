# Anti-Tetris — технологический стек

## 1. Общая архитектура

Anti-Tetris представляет собой полностью клиентскую браузерную игру.

Приложение не использует backend и не требует серверного API. Вся игровая логика, генерация уровней, обработка действий пользователя и хранение состояния выполняются непосредственно в браузере.

Основные части приложения:

```text
Browser
│
├── UI Layer
│   ├── меню
│   ├── выбор уровня
│   ├── таймер
│   ├── отображение прогресса
│   └── экран результата
│
├── Game Engine
│   ├── игровое поле
│   ├── тетримино
│   ├── проверка доступности фигур
│   ├── обработка кликов
│   ├── штрафы
│   └── завершение уровня
│
├── Level Generator
│   ├── правила уровня
│   ├── генерация стакана
│   └── проверка корректности генерации
│
├── Renderer
│   └── WebGL
│
└── State
    ├── состояние текущего уровня
    └── общий прогресс пользователя
```

## 2. Основной стек

### TypeScript

Основной язык разработки приложения.

Используется для:

* игровой логики;
* описания фигур и игрового поля;
* генерации уровней;
* управления состоянием;
* взаимодействия с WebGL;
* пользовательского интерфейса;
* работы с браузерными API.

TypeScript позволяет формализовать основные игровые сущности:

```ts
type TetrominoType =
  | "I"
  | "J"
  | "L"
  | "O"
  | "S"
  | "T"
  | "Z";
```

## 3. Сборка приложения

### Vite

Vite используется как инструмент разработки и сборки frontend-приложения.

Он отвечает за:

* локальный dev-сервер;
* Hot Module Replacement;
* сборку production-версии;
* обработку TypeScript;
* импорт игровых ресурсов;
* оптимизацию итогового bundle.

Приложение после сборки является набором статических файлов:

```text
dist/
├── index.html
├── assets/
│   ├── *.js
│   ├── *.css
│   ├── *.png
│   └── *.ogg
```

Эти файлы могут размещаться на любом статическом хостинге или CDN.

## 4. Рендеринг

### PixiJS

Для визуализации игры используется PixiJS.

PixiJS предоставляет высокоуровневый API для отрисовки 2D-графики с аппаратным ускорением и подходит для игрового поля Anti-Tetris значительно лучше, чем непосредственная работа с низкоуровневым WebGL API.

PixiJS используется для:

* отображения игрового стакана;
* отображения тетримино;
* анимации удаления фигур;
* эффектов при успешных действиях;
* эффектов при ошибочном клике;
* частиц;
* переходов между состояниями;
* визуальных эффектов завершения уровня.

Основной способ рендеринга:

```text
PixiJS
   ↓
WebGL
   ↓
GPU
```

Игровое поле имеет логический размер:

```text
10 × 20 клеток
```

При этом его визуальный размер может динамически масштабироваться под размер экрана пользователя.

---

## 5. WebGL

WebGL является основным графическим API игры.

Непосредственная работа игровой логики с WebGL не предполагается. Взаимодействие осуществляется через PixiJS.

Это позволяет отделить:

```text
Game Logic
    ↓
Scene / Sprites
    ↓
PixiJS
    ↓
WebGL
```

от конкретных деталей работы GPU.

WebGL используется для аппаратно ускоренной отрисовки:

* фигур;
* анимаций;
* glow-эффектов;
* blur;
* частиц;
* шейдерных эффектов;
* transitions.

## 6. Пользовательский интерфейс

Интерфейс, не относящийся непосредственно к игровому полю, реализуется стандартными средствами браузера:

* HTML;
* CSS;
* TypeScript.

К DOM-интерфейсу относятся:

* главное меню;
* выбор уровня;
* кнопки;
* настройки;
* таймер;
* информация о результате;
* экраны победы и поражения.

Игровое поле при этом отображается внутри:

```html
<canvas>
```

Таким образом:

```text
HTML / CSS
    ↓
Menu / HUD / Screens

Canvas
    ↓
PixiJS
    ↓
WebGL
    ↓
Game
```

Использование React или другого frontend-фреймворка на начальном этапе не требуется.

## 7. Состояние игры

Состояние разделяется на два типа.

### 7.1. Состояние текущего уровня

Содержит информацию о текущей игровой сессии:

```ts
interface GameState {
  levelId: number;

  board: BoardState;

  remainingTetrominoes: Tetromino[];

  elapsedTime: number;

  remainingTime: number;

  penalties: number;

  status:
    | "playing"
    | "paused"
    | "completed"
    | "failed";
}
```

Состояние текущего уровня хранится преимущественно в памяти приложения.

При необходимости восстановления уровня после случайной перезагрузки страницы оно может дополнительно сериализоваться в:

```text
sessionStorage
```

`sessionStorage` используется потому, что состояние текущей партии относится только к текущей пользовательской сессии.

После окончания уровня временное состояние удаляется.

## 8. Общий прогресс

Отдельно хранится долгосрочный прогресс пользователя.

Например:

```ts
interface PlayerProgress {
  unlockedLevels: number[];

  completedLevels: number[];

  levelResults: Record<
    number,
    {
      bestTime?: number;
      bestScore?: number;
      stars?: number;
    }
  >;
}
```

Прогресс должен сохраняться между запусками игры.

Для этого используется:

```text
localStorage
```

Пример:

```text
anti-tetris:progress
```

Схема хранения:

```text
Memory
│
├── текущая игровая модель
│
├── sessionStorage
│   └── незавершённый текущий уровень
│
└── localStorage
    └── постоянный прогресс пользователя
```

Backend для хранения прогресса не требуется.

Следствием такого подхода является то, что прогресс привязан к конкретному браузеру и устройству пользователя.

## 9. Управление состоянием

Использование Redux или аналогичных крупных state-management библиотек не требуется.

Игровое состояние рекомендуется реализовать в виде отдельного объекта/store:

```text
GameStore
│
├── state
│
├── startLevel()
├── selectTetromino()
├── removeTetromino()
├── applyPenalty()
├── tick()
├── completeLevel()
└── failLevel()
```

Renderer не должен самостоятельно изменять состояние игры.

Правильный поток:

```text
User Input
    ↓
Game Logic
    ↓
Game State
    ↓
Renderer
```

Например:

```text
Click
 ↓
Определение фигуры
 ↓
Проверка возможности удаления
 ↓
Изменение GameState
 ↓
Анимация PixiJS
```

## 10. Игровая логика

Игровая логика должна быть полностью независимой от PixiJS.

Основные сущности:

```text
Board
Tetromino
Cell
Level
LevelRules
GameState
PlayerProgress
```

Например:

```ts
interface Cell {
  x: number;
  y: number;
}

interface Tetromino {
  id: string;
  type: TetrominoType;
  cells: Cell[];
}
```

Проверка возможности удаления фигуры должна выполняться исключительно над логической моделью игрового поля.

```ts
canRemoveTetromino(
  tetromino: Tetromino,
  board: BoardState
): boolean;
```

Это позволяет тестировать игровую механику независимо от графики.

---

## 11. Генератор уровней

Генератор уровней является отдельным модулем.

Входные данные:

```ts
interface LevelRules {
  heightFill: number;

  timeLimit: number;

  penaltySeconds: number;

  tetrominoDistribution: Partial<
    Record<TetrominoType, number>
  >;
}
```

Пример:

```ts
{
  heightFill: 0.7,

  timeLimit: 90,

  penaltySeconds: 3,

  tetrominoDistribution: {
    I: 0.1,
    J: 0.15,
    L: 0.15,
    O: 0.1,
    S: 0.15,
    T: 0.2,
    Z: 0.15
  }
}
```

Генератор формирует начальную конфигурацию стакана согласно правилам конкретного уровня.

Архитектурно генератор не должен зависеть от Renderer.

```text
LevelRules
     ↓
LevelGenerator
     ↓
BoardState
     ↓
Game Engine
     ↓
Renderer
```

## 12. Анимации

Основные игровые анимации реализуются средствами PixiJS.

Для более сложных последовательностей может использоваться GSAP.

Примеры анимаций:

* фигура улетает вверх;
* shake при заблокированной фигуре;
* подсветка выбранной фигуры;
* glow доступной фигуры;
* исчезновение частиц;
* изменение таймера;
* завершение уровня.

Состояние игры при этом не должно зависеть от состояния анимации.

## 13. Звук

Для воспроизведения звуков используется браузерный:

```text
Web Audio API
```

При необходимости поверх него может использоваться небольшая специализированная библиотека, например Howler.js.

Звуковые события:

```text
tetromino-selected
tetromino-removed
tetromino-blocked
penalty
level-complete
level-failed
```

Игровая логика генерирует событие, а аудиосистема отвечает за его воспроизведение.

## 14. События

Для уменьшения связанности компонентов рекомендуется использовать простую событийную модель.

Например:

```text
GameEngine
   ↓
EventBus
   ├── Renderer
   ├── Audio
   ├── HUD
   └── Effects
```

Пример событий:

```ts
type GameEvent =
  | "tetromino:removed"
  | "tetromino:blocked"
  | "timer:changed"
  | "level:completed"
  | "level:failed";
```

## 15. Тестирование

### Vitest

Для unit-тестов используется Vitest.

В первую очередь тестируется игровая логика:

* корректность размещения фигур;
* определение заблокированной фигуры;
* возможность удаления фигуры;
* генерация стакана;
* правила уровня;
* штрафы;
* условия победы;
* условия поражения;
* сохранение прогресса.

Renderer и WebGL не должны требоваться для выполнения большинства unit-тестов.

Пример структуры:

```text
src/
├── game/
│   ├── Board.ts
│   ├── Tetromino.ts
│   ├── GameEngine.ts
│   └── LevelGenerator.ts
│
├── renderer/
│   └── PixiRenderer.ts

├── audio/
│   └── AudioManager.ts
│
├── state/
│   ├── GameStore.ts

    └── ProgressStorage.ts
```

## 17. Основные архитектурные принципы

1. **Game Logic не зависит от Renderer.**

   Игровые правила работают с абстрактным состоянием клеток и фигур и ничего не знают о WebGL.

2. **PixiJS отвечает только за отображение.**

   Renderer получает состояние игрового мира и отображает его на Canvas.

3. **Текущий уровень и общий прогресс являются разными состояниями.**

   Текущий уровень существует в рамках игровой сессии, а прогресс по уровням сохраняется между запусками игры.

4. **Backend отсутствует.**

   Все вычисления производятся на устройстве пользователя.

5. **Уровни описываются конфигурацией.**

   Новый уровень должен по возможности добавляться изменением `LevelRules`, а не изменением игрового движка.

6. **WebGL используется через PixiJS.**

   Низкоуровневая работа с WebGL допускается только для специализированных shader-эффектов.

7. **Игровое поле является детерминированной моделью данных.**

   Визуальное положение объектов является отображением логического состояния, а не источником истины.
