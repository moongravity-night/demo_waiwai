# Anti-Tetris — Design System

## 1. Назначение

Документ определяет визуальный язык, UI-компоненты, принципы анимации и правила отображения игрового мира Anti-Tetris.

Основной визуальный референс — **Monument Valley**.

Из референса заимствуются принципы:

* минималистичный интерфейс;
* игровая сцена важнее HUD;
* интерфейс воспринимается как часть игрового мира;
* чистые геометрические формы;
* мягкая светлая палитра;
* выразительные, но спокойные цвета;
* минимум текста;
* плавные переходы между состояниями;
* отсутствие визуального шума;
* ощущение физического объекта или архитектурной композиции;
* каждое действие пользователя получает понятный визуальный и звуковой отклик.

Дизайн не должен напрямую копировать конкретные элементы Monument Valley.

---

# 2. Основная дизайн-концепция

Anti-Tetris должен восприниматься не как классический аркадный Tetris, а как **пространственная головоломка с объектами**.

Стакан представляет собой аккуратно собранную композицию из тетрамино.

Пользователь постепенно разбирает эту композицию.

Главный визуальный принцип:

> Игровое поле — это объект. UI существует вокруг него, а не поверх него.

На экране должно быть минимальное количество постоянных элементов.

Основное внимание пользователя всегда находится на:

1. стакане;
2. фигурах;
3. возможности взаимодействия с ними;
4. реакции мира на действие пользователя.

---

# 3. Visual Language

## 3.1. Общий стиль

Стиль:

* minimalist;
* architectural;
* soft;
* tactile;
* calm;
* premium;
* playful.

Не использовать:

* cyberpunk;
* neon UI;
* sci-fi HUD;
* arcade UI;
* большое количество рамок;
* стеклянные панели;
* gradients ради декоративности;
* выраженный skeuomorphism;
* стандартный web-dashboard style.

Интерфейс не должен выглядеть как веб-приложение.

---

# 4. Цветовая система

## 4.1. Фон

Основной фон:

```text
background-primary: #F4F0E8
```

Дополнительный фон:

```text
background-secondary: #E9E2D6
```

Тёплый светлый фон предпочтительнее абсолютно белого.

Допускаются очень мягкие вариации цвета между уровнями.

Примеры:

```text
Warm Sand     #F4F0E8
Soft Rose     #F2E3DF
Mist Blue     #E4ECEC
Pale Mint     #E5EEE4
Warm Lavender #ECE6EF
```

Уровень может иметь собственный оттенок окружения, но структура интерфейса остаётся неизменной.

---

## 4.2. Основной текст

```text
text-primary:   #313136
text-secondary: #777479
text-muted:     #AAA5A3
```

Чистый `#000000` не использовать.

---

# 5. Цвета тетрамино

Фигуры являются самыми насыщенными объектами сцены.

Каждый тип фигуры имеет собственный стабильный цвет.

```text
I — #64B6C4
J — #6379B8
L — #E8A75C
O — #E4CF63
S — #7EB98A
Z — #D87972
T — #A782B8
```

Цвета:

* умеренно насыщенные;
* слегка приглушённые;
* без neon saturation;
* должны хорошо различаться между собой.

Один тип фигуры всегда использует один и тот же основной цвет.

---

# 6. Материал фигур

Тетрамино должны восприниматься как небольшие физические объекты.

Базовая модель:

```text
Material:
- matte
- roughness: 0.65–0.8
- metallic: 0
```

Допускается:

* очень мягкий diffuse lighting;
* лёгкий ambient occlusion;
* небольшой bevel граней;
* мягкая тень;
* минимальный specular highlight.

Не использовать:

* chrome;
* сильные отражения;
* glass;
* plastic gloss;
* emissive/neon материалы.

---

# 7. Геометрия

Основной строительный элемент — клетка.

Фигура должна визуально читаться как единый объект, а не как четыре независимых куба.

Рекомендуется:

```text
cell size: 1 unit
cell gap: 0–2%
corner radius / bevel: 4–8% cell size
```

На внутренних границах фигуры допускается лёгкое разделение клеток.

Внешний силуэт фигуры должен быть хорошо читаемым.

---

# 8. Игровой стакан

Размер логической сетки:

```text
width: 10 cells
height: 20 cells
```

Стакан является центральным объектом сцены.

Визуально он не должен выглядеть как тяжёлая рамка.

Предпочтительный вариант:

* отсутствует полноценная внешняя рамка;
* границы считываются по расположению фигур;
* нижняя поверхность или основание обозначены визуально;
* допустим едва заметный контур сетки.

Сетка:

```text
opacity: 4–8%
```

Она должна помогать ориентации, но не конкурировать с фигурами.

---

# 9. Перспектива

Основной вариант — почти ортографическая камера.

```text
Projection: orthographic
```

Допустим небольшой псевдоизометрический наклон для создания ощущения физической композиции.

Камера не должна мешать чтению сетки.

Приоритет:

```text
gameplay readability > visual perspective
```

Ячейки должны оставаться визуально однозначными.

---

# 10. Композиция экрана

## Desktop

Основная структура:

```text
┌─────────────────────────────────────────┐
│ Level 04                       01:24     │
│                                         │
│                                         │
│                GAME                     │
│                FIELD                    │
│                                         │
│                                         │
│                       ⚙                 │
└─────────────────────────────────────────┘
```

Игровой стакан:

* расположен по центру;
* занимает основную часть доступной высоты;
* имеет большое количество свободного пространства вокруг.

HUD располагается по краям viewport.

---

# 11. HUD

Постоянный HUD должен содержать только критически важную информацию.

Основные элементы:

```text
Level
Timer
Pause / Settings
```

Опционально:

```text
Penalty
Progress
```

HUD не должен использовать отдельные панели без необходимости.

Плохо:

```text
┌──────────────┐
│ LEVEL 4      │
└──────────────┘
```

Хорошо:

```text
LEVEL 04
```

---

# 12. Typography

Основной характер:

* geometric sans-serif;
* humanist;
* rounded;
* clean.

Подходящие направления:

```text
Inter
Manrope
Avenir-like
Nunito Sans
Geist
```

Предпочтительно использовать один шрифт.

## Размеры

```text
Display / Result     48–72 px
Timer                28–40 px
Level                16–20 px
Button               16–18 px
Body                 14–16 px
Caption              12–14 px
```

Использовать небольшое количество font weights:

```text
Regular 400
Medium 500
Semibold 600
```

Bold используется редко.

---

# 13. Таймер

Таймер — главный постоянный информационный элемент.

Пример:

```text
01:42
```

Не использовать дополнительные подписи вроде:

```text
TIME REMAINING
```

если контекст очевиден.

## Состояния

### Normal

```text
color: text-primary
```

### Warning

Последние 20% времени:

```text
color: #D18A64
```

### Critical

Последние 10 секунд:

```text
color: #C95F59
```

Допускается мягкая анимация scale или opacity.

Запрещено агрессивное постоянное мигание.

---

# 14. Интерактивность фигур

Фигура является основной кнопкой игры.

Она не должна выглядеть как обычный UI control.

## Default

```text
scale: 1
brightness: 1
```

## Hover

Фигура слегка реагирует на указатель:

```text
translateY: -2–4 px equivalent
brightness: +5%
shadow: slightly stronger
duration: 120–160 ms
```

Реакция должна быть очень лёгкой.

---

# 15. Доступная для удаления фигура

Не следует постоянно подсвечивать все доступные фигуры.

Игрок должен самостоятельно анализировать конструкцию.

При hover допускается подчёркивать возможность действия:

```text
cursor: pointer
small lift
soft shadow
```

После клика фигура начинает удаляться.

---

# 16. Удаление фигуры

Удаление — главное положительное действие игры.

Анимация должна доставлять удовольствие.

Последовательность:

```text
click
↓
small compression
↓
release
↓
rapid upward movement
↓
slight acceleration
↓
fade / dissolve outside scene
```

Пример timings:

```text
compression: 60 ms
release: 80 ms
flight: 350–550 ms
fade: final 100 ms
```

Допускается небольшой `squash & stretch`.

### Squash

```text
scaleY: 0.96
scaleX: 1.02
```

### Release

```text
scaleY: 1.03
scaleX: 0.99
```

После этого фигура возвращается к нормальной пропорции во время движения.

---

# 17. Траектория удаления

Фигура должна преимущественно двигаться вертикально вверх.

Допускается очень небольшой lateral drift:

```text
0–0.15 cell
```

Не использовать хаотические траектории.

Основная метафора:

> фигура освобождается из конструкции.

---

# 18. Заблокированная фигура

При клике на фигуру, которую нельзя удалить, действие не выполняется.

Не использовать стандартные UI-ошибки вроде:

```text
ERROR
INVALID MOVE
```

Ответ должен быть физическим.

Последовательность:

```text
click
↓
small movement upward
↓
immediate resistance
↓
return
```

Дополнительно фигура может слегка:

```text
shake: 1–2 px
duration: 180–240 ms
```

Фигуры, которые непосредственно блокируют выбранную, могут получить очень короткий визуальный акцент:

```text
brightness +8%
duration: 250 ms
```

Это помогает пользователю понять причинно-следственную связь.

---

# 19. Штраф

Штраф отображается максимально ненавязчиво.

Например:

```text
−3s
```

Появляется рядом с таймером или над фигурой.

Animation:

```text
fade in
move upward 8–12 px
fade out
```

Duration:

```text
600–900 ms
```

Не использовать отдельный modal или toast.

---

# 20. Выделение блокирующих фигур

При ошибочном клике система может визуально показать причину блокировки.

Выделяются только фигуры, реально препятствующие движению вверх.

Рекомендуемая реакция:

```text
selected blocked piece:
  small downward return animation

blocking pieces:
  subtle pulse
```

Duration:

```text
200–350 ms
```

Это одновременно является feedback и обучением правилам игры.

---

# 21. Эффекты

VFX должны поддерживать действие, но не доминировать.

## Допустимые эффекты

* небольшие частицы;
* dust;
* soft glow;
* subtle trail;
* ambient particles;
* shadow animation;
* небольшое изменение освещения.

## Не использовать

* explosions;
* fire;
* intense bloom;
* screen shake;
* большое количество confetti;
* постоянные частицы вокруг фигур.

---

# 22. Частицы при удалении

Во время успешного удаления допускается 4–12 небольших частиц.

Они должны:

* соответствовать цвету фигуры;
* быстро исчезать;
* двигаться преимущественно вверх;
* иметь небольшой разброс.

Lifetime:

```text
250–500 ms
```

Particle size:

```text
2–6% cell size
```

---

# 23. Освещение

Освещение должно быть мягким и архитектурным.

Базовая модель:

```text
1 key directional light
1 ambient / hemisphere light
ambient occlusion
soft shadows
```

Избегать нескольких цветных источников.

Источник света визуально расположен сверху и немного сбоку.

Тени:

```text
soft
low contrast
short-medium distance
```

---

# 24. Окружение

Игровой стакан не должен висеть в абстрактном UI-пространстве.

Допускается минимальная сценография:

* платформа;
* пьедестал;
* мягкая плоскость;
* архитектурный фон;
* небольшие геометрические декоративные элементы.

Однако окружение никогда не должно усложнять чтение сетки.

---

# 25. Начало уровня

Начало уровня происходит без тяжёлого loading screen.

Последовательность:

```text
background visible
↓
platform appears
↓
pieces softly appear / assemble
↓
HUD fades in
↓
game becomes interactive
```

Продолжительность:

```text
800–1500 ms
```

---

# 26. Level Intro

Минимальный вариант:

```text
LEVEL 04
```

Под ним допускается короткое название:

```text
THE TOWER
```

Через 1–1.5 секунды надпись исчезает.

Если пользователь начинает взаимодействовать раньше — intro немедленно заканчивается.

---

# 27. Level Complete

Завершение уровня должно восприниматься как отдельный эмоциональный момент.

Не показывать мгновенно обычный modal.

Последовательность:

```text
last piece removed
↓
short pause
↓
scene reacts
↓
timer stops
↓
camera / lighting transition
↓
result appears
```

Пример:

```text
LEVEL COMPLETE

01:14

Continue
```

Но предпочтительнее ещё меньше текста:

```text
04

COMPLETED

01:14
```

---

# 28. Экран победы

UI располагается непосредственно поверх композиции или заменяет её.

Фон уровня остаётся видимым.

Кнопка продолжения может быть представлена:

```text
→
```

или минимальной текстовой кнопкой:

```text
Continue
```

Не использовать большую стандартную modal-card.

---

# 29. Переход между уровнями

Переход должен ощущаться непрерывным.

Предпочтительно:

```text
current world fades / moves away
↓
background shifts
↓
next world emerges
```

Вместо:

```text
Level Complete
→
Loading Screen
→
Menu
→
Loading Screen
→
Next Level
```

---

# 30. Выбор уровней

Экран выбора уровней должен восприниматься как отдельная игровая композиция.

Не использовать стандартную таблицу:

```text
[1] [2] [3] [4]
[5] [6] [7] [8]
```

Предпочтительный подход — набор небольших архитектурных объектов или символов.

Например:

```text
      ◇

  △       □

      ○

  ▱       ◇
```

Каждый объект представляет уровень.

---

# 31. Состояния уровня

## Locked

```text
opacity: 25–40%
interaction: disabled
```

Необязательно использовать lock icon.

## Available

```text
opacity: 100%
```

## Completed

Допускается небольшой дополнительный визуальный знак:

```text
dot
small star
subtle pedestal
different elevation
```

Не использовать большие зелёные checkmark.

---

# 32. Tutorial

Обучение должно происходить через сам игровой мир.

Предпочтительно:

1. подсветить фигуру;
2. показать курсор/палец;
3. продемонстрировать движение вверх;
4. дать пользователю повторить действие.

Текст используется только если визуального объяснения недостаточно.

Пример текста:

```text
Remove a free piece
```

Лучше, чем:

```text
Click on a tetromino that does not have another tetromino above any of its cells.
```

---

# 33. Cursor

Desktop:

```text
default → standard cursor
interactive figure → pointer
drag interaction → grab/grabbing
```

Допускается собственный минимальный курсор, но он не должен ухудшать usability.

---

# 34. Кнопки

UI-кнопки используются редко.

## Primary

Пример:

```text
Continue
```

Стиль:

```text
background: transparent
text: text-primary
font-weight: 500
```

Hover:

```text
opacity: 0.65
```

Или underline / небольшое движение.

Не использовать большие filled CTA без необходимости.

---

# 35. Icon Buttons

Используются для:

```text
pause
sound
restart
settings
fullscreen
```

Размер visual icon:

```text
20–24 px
```

Hit area:

```text
44×44 px minimum
```

Иконки:

* простые;
* stroke-based;
* одинаковой толщины;
* без декоративной детализации.

---

# 36. Pause

Pause не должен полностью разрушать композицию.

При паузе:

```text
scene brightness: -10%
game interactions: disabled
```

По центру:

```text
Continue
Restart
Exit
```

Без большой card background.

---

# 37. Sound Design

Аудио является частью дизайн-системы.

Характер:

* soft;
* tactile;
* ASMR-like;
* physical;
* satisfying.

## Successful removal

Комбинация:

```text
soft click
+
ceramic / wooden release
+
short airy whoosh
```

## Blocked click

```text
muted knock
```

## Level complete

```text
short melodic chord
```

Не использовать громкие arcade sounds.

---

# 38. Ambient Audio

Допускается очень тихий ambient layer.

Например:

* wind;
* room tone;
* distant harmonic texture;
* soft environmental sounds.

Ambient не должен отвлекать от игровых звуков.

---

# 39. Animation Principles

Все движения должны выглядеть:

```text
soft
deliberate
physical
predictable
```

Основной easing:

```text
ease-out
```

Для физических объектов допустим spring easing с минимальным overshoot.

---

# 40. Animation Durations

```text
Hover              120–160 ms
Button              120–200 ms
Blocked feedback    180–250 ms
Piece removal       350–550 ms
UI appear           250–400 ms
Level transition    800–1500 ms
Level complete      1000–1800 ms
```

Не использовать одинаковую длительность для всех действий.

---

# 41. Motion Hierarchy

Скорость движения отражает значимость действия.

```text
hover          → very fast
click feedback → fast
piece removal  → medium
screen change  → slow
level complete → slowest
```

---

# 42. Responsive Design

Игровая область всегда является приоритетом.

## Desktop

Стакан занимает:

```text
60–80% viewport height
```

## Mobile

Стакан занимает:

```text
65–85% viewport height
```

HUD адаптируется вокруг стакана.

Нельзя уменьшать стакан ради сохранения desktop-layout.

---

# 43. Safe Area

Минимальные отступы:

```text
Desktop: 24–40 px
Mobile: 16–24 px
```

На устройствах с notch использовать:

```css
env(safe-area-inset-top)
env(safe-area-inset-right)
env(safe-area-inset-bottom)
env(safe-area-inset-left)
```

---

# 44. WebGL Rendering

Всё, что непосредственно относится к игровой сцене, предпочтительно рендерить через WebGL:

```text
tetrominoes
game board
platform
lighting
shadows
particles
world transitions
gameplay animations
```

UI допустимо реализовывать DOM/CSS поверх WebGL:

```text
timer
level number
menu
settings
pause
accessibility controls
```

При этом визуально DOM и WebGL должны восприниматься как единая система.

---

# 45. Performance

Цель:

```text
60 FPS
```

Минимально допустимое стабильное состояние:

```text
30 FPS
```

Предпочтительно использовать:

* instanced geometry;
* shared materials;
* texture atlases при необходимости;
* object pooling для частиц;
* минимальное количество dynamic lights;
* ограниченное количество realtime shadows.

Красота эффекта не должна приводить к заметной задержке взаимодействия.

---

# 46. Input Feedback

Визуальная реакция на click/touch должна начинаться практически мгновенно.

Целевая задержка:

```text
< 100 ms
```

Игрок должен сразу понимать, что действие зарегистрировано.

---

# 47. Accessibility

Минимальные требования:

* цвет фигуры не является единственным способом различения;
* формы тетрамино всегда читаются геометрически;
* достаточный contrast текста;
* interactive hit area минимум 44×44 px;
* поддержка `prefers-reduced-motion`;
* возможность отключить звук;
* возможность отключить ambient sound.

При `prefers-reduced-motion`:

* убрать сложные camera transitions;
* уменьшить fly animations;
* исключить decorative motion;
* сохранить функциональный feedback.

# 53. Design Rules

## Rule 1

Gameplay важнее decoration.

Если декоративный элемент мешает определять положение клетки — удалить декоративный элемент.

## Rule 2

Минимум UI.

Если информацию можно показать через состояние игрового объекта — не создавать отдельный UI-компонент.

## Rule 3

Motion объясняет состояние.

Анимации должны показывать:

```text
можно удалить
нельзя удалить
фигура удалена
уровень завершён
```

а не существовать исключительно для красоты.

## Rule 4

Цвет принадлежит игровому миру.

Самые насыщенные цвета используются фигурами.

UI остаётся нейтральным.

## Rule 5

Каждый экран должен выглядеть как композиция.

Не заполнять свободное пространство интерфейсом только потому, что оно свободно.

Пустое пространство является частью дизайна.

---

# 54. Do

Использовать:

* большие свободные области;
* чистую геометрию;
* спокойные фоны;
* мягкие тени;
* матовые материалы;
* плавные движения;
* маленькое количество UI;
* физический feedback;
* цвет для игровых объектов;
* короткие тексты.

---

# 55. Don't

Не использовать:

* glassmorphism;
* neon;
* большие панели HUD;
* gradient-heavy интерфейс;
* cyberpunk эстетику;
* лишние рамки;
* RGB glow;
* постоянную подсветку доступных ходов;
* большие уведомления об ошибках;
* стандартные browser-like controls;
* агрессивный screen shake;
* слишком большое количество particles;
* постоянные tutorial popups.

---

# 56. Итоговый визуальный образ

Anti-Tetris должен ощущаться как:

> спокойная интерактивная архитектурная головоломка, состоящая из цветных физических объектов.

Не как:

> классический Tetris с новым игровым правилом.

Пользователь должен получать удовольствие не только от решения головоломки, но и от самого процесса разбора конструкции:

```text
hover
→
click
→
release
→
flight
→
sound
→
space opens
```

Каждое удаление фигуры должно быть маленьким завершённым визуальным событием.

Вся дизайн-система строится вокруг трёх принципов:

**Clarity. Tactility. Calm.**
